======================================================================
〇  总原理：算力全程在 Google 那边
======================================================================

客户端库 @google/earthengine **不做任何计算**。

它只是把脚本里的 JS 调用翻译成一段 JSON（一张"计算图"），POST 给 Google
的 REST 接口；服务器算完，返回 JSON。本地从头到尾只干三件事：
**拼 JSON、发 HTTP、解析 JSON。**


〇.1  实际发生的事
----------------------------------------------------------------------

脚本里的这一行：

    var ndvi = ee.Image('COPERNICUS/S2_SR_HARMONIZED/...')
                 .normalizedDifference(['B8', 'B4']);

客户端库**一次运算都没做**。它只记了一棵表达式树：

    {
      函数: "Image.normalizedDifference",
      输入: { 函数: "Image.load", id: "..." },
      参数: ["B8", "B4"]
    }

直到调用 getInfo()，才发生下面这一串：

        本地 JS 对象树
           ↓ 序列化
        一段 JSON（计算图）
           ↓ HTTPS POST + Bearer token
        earthengine.googleapis.com/v1/projects/<项目>/value:compute
           ↓ Google 的机房真算
        返回 JSON 结果
           ↓ 反序列化
        本地 JS 值

算力全程在 Google 那边。本地这一侧从头到尾只干了三件事：
拼 JSON、发 HTTP、解析 JSON。


〇.2  那么 Code Editor 到底多干了什么
----------------------------------------------------------------------

只有界面：

┌─────────────────┬───────────────────────────────────────────┐
│   Code Editor   │                   实质                    │
├─────────────────┼───────────────────────────────────────────┤
│ print(x)        │ 调 getInfo() → 把返回的 JSON 画到右边面板 │
├─────────────────┼───────────────────────────────────────────┤
│ Map.addLayer(x) │ 向服务端要瓦片图片，贴到地图上            │
├─────────────────┼───────────────────────────────────────────┤
│ Export.*        │ 向服务端提一个后台任务，出现在 Tasks 面板 │
├─────────────────┼───────────────────────────────────────────┤
│ ui.*            │ 纯前端控件                                │
└─────────────────┴───────────────────────────────────────────┘

**没有一项参与计算。** 它就是个带地图的 REST 客户端。


〇.3  于是本地跑起来只有三个必要条件
----------------------------------------------------------------------

  1. **有人能拼那棵树**
     → npm 的 @google/earthengine 就是干这个的，与 Code Editor 里跑的是
       同一份 Google 官方 JS，所以脚本一个字都不用改。

  2. **有 token**
     → 用 earthengine authenticate 存下的 refresh_token 换 access_token。

  3. **那个 POST 出得去**
     → 这台机器要走代理，而 EE 客户端的 HTTP 出口被 npm 包 xmlhttprequest
       锁死、又不读代理，所以把出口整个换成自己的实现。

  三条齐了，就通了。

至于 print / Map / Export / ui 这层在本地补出来的外壳，是为了让脚本别在
这几行上崩，**与"能不能算"无关**；唯一有实质作用的，是把 print 实现成
真的调 getInfo() —— 不调它，那棵树永远只是棵树，一个字节都不会发出去，
脚本会秒过而什么都没验证。

推论 —— 这也是整件事的判据：

    "本地能不能跑 GEE"这个问题，
    等价于"这个 POST 发不发得出去，手上有没有有效的 token"。

与本机装没装遥感软件、内存多大、有没有独立显卡一概无关。

下面三节按上面三个条件逐条展开，第四节讲为什么这件事以前一直没做成。


======================================================================
一  条件一 · 拼那棵树 —— 惰性计算是唯一的杠杆
======================================================================

1.1  三个推论，全都很要紧
----------------------------------------------------------------------

既然写一行代码只是在攒树、服务器什么都没算：

① **语法检查毫无用处。**
   波段名写错、集合被过滤成空、归约器参数个数不对 —— 攒树阶段一律不报错，
   node --check 全过，静态审读同样看不出来。

② **脚本"执行完不报错"完全不等于代码是对的。**
   没有任何东西去触发计算的话，脚本从头跑到尾一声不响，什么也没发生。
   这是一个彻头彻尾的假象。

③ **报错的行号往往不是有 bug 的行。**
   错误统一在 print / addLayer 那一刻爆出来。实测过一次：森林扰动脚本
   报错的 print 在第 250 行，真正的 bug 在第 141 行。


1.2  杠杆架在推论 ② 上
----------------------------------------------------------------------

测试台真正起作用的地方**只有一处**：

    把 print(x) 实现成真的调用 x.getInfo()。

getInfo() 是"提交计算图、阻塞等结果"的同步调用。它一执行，那棵表达式树
就被序列化提交，服务端就真的开始算，结果（或报错）原样回来。

于是脚本里的每一个 print 都变成一次真实的服务端计算 —— 写错的波段名、
过滤成空的集合、参数个数不对的归约器，全部在这一刻暴露。

外壳的其余部分都是配角，**只有这一条是发动机**。
也正因如此，一个 print 都不写的脚本，这套工具查不出任何东西 —— 它没有
杠杆可用。这不是工具的缺陷，是原理决定的边界。

★ 这与 GEE 教材里讲的"客户端对象／服务端对象、惰性计算"是同一条原理，
  只是用途反过来：教材讲它，是为了让人理解"为什么改一行代码看不到任何
  反应"；这里则是把它当**测试杠杆**用 —— 凡是能被 getInfo() 拉动的
  错误，就都查得出来。


======================================================================
二  条件二 · 那层外壳 —— 为什么可以做成假的
======================================================================

2.1  计算层拿得到，界面层拿不到
----------------------------------------------------------------------

    层        是什么                              本地拿不拿得到
    --------  ----------------------------------  ------------------
    计算层    ee.Image / ee.Reducer /             有  就是 npm 上的
              ee.Algorithms / ee.Geometry …         @google/earthengine
    界面层    print / Map / Export / ui / Chart   无  只存在于编辑器
                                                    那个网页里

本地缺的**不是计算能力，是那层外壳**。而按〇.2，外壳里没有一样参与计算，
所以**把它做成假的不削弱测试的有效性** —— 真的那一份原本也不做计算。
真假之别只在"看得见图"与"看不见图"，与"算得对不对"无关。


2.2  四个替身各自还多做了一点事
----------------------------------------------------------------------

    print(x)
        真调 getInfo()，结果打到终端；服务端报错原样抓进错误清单。
        （见 1.2，这是唯一的发动机。）

    Map.addLayer(x, vis, name)
        不要瓦片，改对 x 取一次 bandNames()。
        用意有二：一是**多触发一次计算**，多一个杠杆；二是若返回空数组
        即告警"零波段影像" —— 这正是"空集合取 median()"的病征，在真
        Code Editor 里只表现为"图层一片空白"，很容易被忽略。
        若 x 不是影像而是要素集，则改取 size()。

    Export.*
        只校验参数并打印，**不真提交任务**。顺带检查 region、scale
        （或 crsTransform）、maxPixels 齐不齐，缺了记告警。
        坚持不真提交是两条实打实的理由：真导出会**消耗计算配额**，并且会
        **往你自己的 Drive / Asset 里写文件**。校验代码不应当有这种
        副作用 —— 尤其是要批量跑十几个脚本的时候。

    ui.*
        返回一个 Proxy 空部件，**任何属性访问都返回一个返回自身的函数**，
        这样 ui.Chart.image.series(...).setOptions(...).setChartType(...)
        这种长链永远不会断。
        （最初写成普通对象、只实现几个方法，结果脚本从链条中间断掉。）


======================================================================
三  条件三 · 那个 POST —— 要换掉的不是"设置"，是 HTTP 出口
======================================================================

这一层是整套工具最难的部分，也是"以前一直打不通"的直接原因。


3.1  起点：getInfo() 是同步调用，而 Node 里没有同步 HTTP
----------------------------------------------------------------------

EE 的 getInfo() 是**同步**的 —— 提交、阻塞、拿到结果再往下走。

在浏览器里这没问题（XMLHttpRequest 支持 async=false）。但 Node 里
**根本没有同步 HTTP**。EE 客户端在 Node 环境下用的是 npm 包
xmlhttprequest，它在 async=false 时的做法是：

    spawnSync 另起一个 Node 子进程去发这个请求，
    父进程阻塞等它退出，再读它 stdout 里的内容。

这句话是本节全部结论的来源。


3.2  由此解释那个百思不解的现象
----------------------------------------------------------------------

现象：

    给 https.globalAgent 打上代理补丁，oauth2.googleapis.com 已经能连通，
    EE 初始化却仍然失败，status 恒为 0。

解释：

    **补丁打在父进程，请求发在子进程。**
    子进程是全新的 Node 进程，父进程内存里那个打过补丁的 globalAgent，
    它根本看不见。

    这不是补丁写错了，是补丁的位置从原理上就够不着。

推而广之：凡是"修改本进程全局对象"的做法，遇上 spawn 出来的子进程一律
失效，不止代理这一例。判断这类问题的第一个问题永远是：**这段代码和那个
请求，跑在同一个进程里吗？**


3.3  正解：换掉出口本身
----------------------------------------------------------------------

自己实现一个 XMLHttpRequest（xhr代理.js 里的 ProxyXHR）：

    路径                        怎么发            代理怎么带
    --------------------------  ----------------  --------------------
    异步 send()                 https.request     agent，进程内直接挂
    同步 send()（getInfo 走这   照样 spawnSync    把代理地址随 stdin 的
    条）                        起子进程          JSON 一起送进子进程，
                                                  由子进程自己
                                                  new HttpsProxyAgent

关键在最后一格：同步路径**保留**子进程方案（在 Node 里同步发 HTTP 没有
别的办法），但让代理信息**跟着请求一起过河**。


3.4  替换点为什么选 Module._load
----------------------------------------------------------------------

只设 global.XMLHttpRequest 不够。@google/earthengine 的 build\main.js
第 2 行自己写着：

    const XMLHttpRequest = require('xmlhttprequest').XMLHttpRequest;

加载那一刻就把我们设的值覆盖回去了。所以要拦在更上游 —— 谁
require('xmlhttprequest')，就把我们这一版给谁：

    const Module = require('module');
    const _load = Module._load;
    Module._load = function (request, parent, isMain) {
      if (request === 'xmlhttprequest') return { XMLHttpRequest: ProxyXHR };
      return _load.apply(this, arguments);
    };

选这个点还有第二个好处：**完全不动 node_modules\**。
直接改第三方包的源码也能达到同样效果，但 npm install 一重装就没了，
换台电脑更是必然复现。拦模块加载改的是我们自己的文件，重装、重拷都不丢。

★ 顺序有硬要求：这段拦截必须在 require('@google/earthengine') **之前**
  执行，晚一步就已经晚了。环境自检.js 也在文件顶部照做一遍 —— 它同样要
  真连服务器。（写自检脚本时又踩过一次，症状是最后一项"真连 EE"莫名
  其妙 ETIMEDOUT。）

★ 代理地址必须**每次现读 process.env**，不能在模块加载时读死。
  启动顺序是「先 require xhr代理.js → 再自动探测代理 → 把结果写进
  process.env」，读死的话探测结果对已加载的模块完全无效，
  症状是"自检说探到了代理，请求还是超时"。


3.5  代理从哪来：四级顺序（代理探测.js）
----------------------------------------------------------------------

按序取**第一个通过验证**的：

    顺序  来源                              验证方式
    ----  --------------------------------  ------------------------
    ①    配置.txt 里的「代理 = …」         用它 HEAD 一次
                                            oauth2.googleapis.com，
                                            通了才采信
    ②    环境变量 HTTPS_PROXY / HTTP_PROXY  同上
    ③    直连（不挂代理）                   同上；通了就直连 ——
                                            不需要代理的网络不绕路
    ④    扫本机常见代理端口                 先并发探"端口开着没"
          10808 / 10809 / 7890 / 7897 /     （约 400 ms），
          1080 / 8080 / 8888 / 2080 / 10000  再逐个真的去连 Google

★ 第 ④ 步里"端口开着"不算数。
  本机开着的端口多得很，可能是别的软件占的，也可能是代理软件开着但没
  连上节点。判据必须是"**用这个代理真的够到了 Google**"，否则会自信地
  选中一个通不了的口，后面全盘失败，还查不出原因。
  ①②两级同样要过这一关：配置里写着、环境变量里设着，都不等于它此刻能用。

定下来之后 apply() 把地址写回 process.env 的 HTTPS_PROXY / HTTP_PROXY；
四级都不通时则把这几个变量**删掉**，免得一个失效的旧值继续拖累后面。
这样后续所有代码 —— 包括 spawnSync 出去的子进程 —— 拿到的都是同一个答案。

★ 为什么不能只靠环境变量：双击 .bat 打开的是全新 cmd 窗口，**不继承**
  你在别处 set 过的值。"命令行里跑得好好的，一双击就连不上 Google"
  就是这么来的。


3.6  重试策略：网络层重试，业务错误不重试
----------------------------------------------------------------------

requestSync 对**网络层失败**（status 为 0 / 502 / 503 / 504）重试 3 次，
退避 3 秒、6 秒；对**服务端返回的业务错误**（带 JSON 的 4xx/5xx）
**一次都不重试**。

这条分界是故意划的：

    网络抖动 —— 重发一次就好，尤其是几百秒的重计算，
                 本地代理偶尔会把长连接掐断；
    业务错误 —— 恰恰是我们要抓的东西。重试它既没有意义
                 （同一张计算图重发一次还是同样的错），
                 又会把一次报错拖成三倍时间。

★ 重试也救不回来时，多半**真的是计算太重**，该改的是脚本不是网络。
  实例：一个分县统计脚本用 30 m 成图尺度在 4.4 万平方公里市域上逐县归约，
  596 秒超时；改用粗的 statScale 后 433 秒跑通。


======================================================================
四  为什么这件事以前一直没做成：两道墙互相伪装
======================================================================

真正的原因不是哪一处技术难，而是：
**两道墙的失败症状，恰好长成对方的样子。**

    真实原因              表面症状                  会被误读成
    --------------------  ------------------------  ------------------
    HTTP 出口不通         Failed to contact Earth   代码写错了
    （第三节）            Engine servers…，          —— 假阴性：把网络
                          或跑到一半断掉             问题算到代码头上
    没有东西触发计算      脚本执行完毕，零报错      代码是对的
    （第一节）                                       —— 假阳性：其实一次
                                                     计算都没发生

一个假阴、一个假阳，凑在一起就得到"本地跑 GEE 这条路走不通"的结论。

拆开之后各自都不难：
一道靠 ProxyXHR 换出口，一道靠 print → getInfo() 拉动计算。

这条教训比工具本身更值钱：**当两类失败的症状会互相伪装时，先把它们分开
各自验证，再下结论。** 具体到这里，分开的办法就是两个互不相干的判据 ——
"HEAD 一次 Google 通不通"（只测网络）与"ee.Number(1).add(1).getInfo()
等不等于 2"（只测计算链路是否真的接通）。环境自检.js 就是照这个思路逐项
排下来的，所以它的输出可以直接当诊断书用。


======================================================================
五  其余几个设计决定的理由
======================================================================

5.1  认证：为什么不用每次登录
----------------------------------------------------------------------

earthengine authenticate 那一次登录，在
%USERPROFILE%\.config\earthengine\credentials 里留下一个 refresh_token，
长期有效。每次启动拿它去 oauth2.googleapis.com/token 换一个约一小时有效
的 access_token 即可，不必再开浏览器。

★ 换令牌用的 client_id / client_secret 是 earthengine-api 开源包里
  **公开分发**的 installed-app client，不是谁的私有凭据 —— OAuth 的
  installed-app secret 按设计就不是秘密。换任何机器都继续有效，不用改。
  但**不要凭记忆补全它**，要从已装的 Python 包里读真值：
      py -3.12 -c "import ee.oauth as O; print(O.CLIENT_ID); print(O.CLIENT_SECRET)"

★ 凭据不在这个仓库里，在用户目录下。所以克隆或拷贝**不会**泄露任何人的
  账号；反过来，新机器**必须**自己认证一次。
  也**绝不要**把 credentials 的内容打印出来或贴进 AI 对话框 ——
  里面的 refresh_token 等同于账号的长期钥匙。

★ 换令牌那个请求的 HTTPS agent 是**现建**的，不能用 https.globalAgent
  —— 代理是刚刚探测出来写进 process.env 的，globalAgent 并没有打过补丁，
  用它会直连然后超时。


5.2  项目 ID：为什么必须有，为什么配置文件按字节解析
----------------------------------------------------------------------

现在的 GEE 不允许无项目初始化，ee.initialize 必须带项目 ID；初始化时
客户端还会去拉一份算法清单（/v1/projects/<项目>/algorithms），这是第一个
会暴露网络问题的地方。

配置.txt 是给人改的，所以要防两件事：

  · **编码**。Windows 记事本默认存 GBK，别处可能存成 UTF-8。若靠"项目ID"
    三个中文字去匹配键名，等于赌文件用哪种编码存 —— 不可靠。所以整个文件
    按 latin1 读字节，键名判据只认 **ASCII 部分**："ID"这两个字母无论
    GBK 还是 UTF-8 都原样是 0x49 0x44，永远认得出来。项目 ID 本身只会是
    ASCII，这样解析完全不受编码影响。

  · **全角符号**。中文输入法下打出全角"＝""："是极常见的事。分隔符必须
    同时认半角与全角，否则会**静默回落到默认值** —— 最难查，表现为
    "我明明改了配置，它还是连上一台机器的项目"。

★ 解析逻辑单独抽在 配置读取.js，跑GEE.js 与 环境自检.js **共用同一份**。
  以前两边各抄一份，出现过"自检说没配置、跑GEE 却读得到"的怪事。


5.3  为什么**不**做"自动跳过某类脚本"（一个撤掉的设计）
----------------------------------------------------------------------

早期版本有这么一个功能：按文件名和正文关键词，自动跳过"填空骨架"类脚本
（含 /* 补全 */ 占位、TODO-N、抬头写着"学生版"的）。当时的理由听着挺对：
这类文件本来就不完整，让它跑，**得到"跑通"是误导，得到"报错"同样是误导**。

撤掉它的理由更硬：

  · 判据是对**文件内容**的猜测，而文件是别人写的。
    任何人的正常脚本里出现一句 // TODO-1 换成研究区，整个文件就被静默跳过。

  · 失败方式是**无声**的。终端只多一行不起眼的"⏭ 跳过"，
    总表那一格是空的，看起来像"没问题"。
    **静默跳过比跑错更难查** —— 跑错至少有报错可循。

  · 它违反了这个工具存在的前提。一个校验工具**绝不能自作主张决定
    "哪些不用校验"**；要排除什么，应该由调用方在**入参**上表达
    （别把它放进 --all 的目录），而不是由工具去猜正文。

现在的行为：交给它的每个 .js 都会真跑，一个不漏。

★ 这条留在这里不是为了记录一个被删的功能，是为了**别再加回来**。
  "帮用户自动判断"这类点子在写的时候总是显得贴心，
  代价要到别人用出问题、而且查不出原因的时候才付。


5.4  沙箱：require / process / module 设为 undefined
----------------------------------------------------------------------

待测脚本在 vm.runInNewContext 里执行，上下文只注入 ee、console、四个界面
外壳，以及 Math / JSON / Date 等标准对象；require、process、module 三项
**显式设为 undefined**。

用意不是防谁作恶（vm 本来也不是安全边界），而是：Code Editor 脚本本来就
用不着这三样，一旦某个脚本里手滑写出 require('fs') 之类的语句，批量跑
十几个文件时会产生看不见的副作用。设成 undefined 让它当场失败，比悄悄
成功好。

同一个调用还带 timeout（单脚本超时，默认 300 秒，--timeout 可调）。


5.5  退出码
----------------------------------------------------------------------

    0   全部脚本无报错
