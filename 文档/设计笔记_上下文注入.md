# 设计笔记 · 上下文注入

> 记录 `new-workspace.js` / `新建工作区.bat` 这个模式：**它为了解决什么、怎么实现的、
> 以后做别的工作流怎么照搬。**
>
> 这份不是使用说明（那在根目录的 `README.md`），是**方法论**。

---

# 一、它解决的是两个问题，不是一个

## 问题 A：每次开局都要人肉交代背景

原来的对话总是这样起头：

> "你先了解一下这个 GEE 测试项目，然后再听我的需求……"

这很浪费，而且**不可靠**——你交代得详细还是潦草，决定了 AI 这一轮的表现。
同一件事说十遍，十遍都不一样。

## 问题 B：在工具目录里干活会污染工具目录

活干多了，工具目录里就混进一堆临时脚本、探针、成果文件、失败的尝试。
半年后你自己都分不清哪些是工具、哪些是垃圾。

而你真正的数据和资料往往在**别的文件夹**——那才是该干活的地方。

## 这两个问题是同一个问题

因为：**如果只能在工具目录里干活，才需要工具目录里有说明；
如果能在任何地方干活，那"说明"就得跟着走。**

所以解法必须同时满足：

1. 工具目录**只读、稳定**，永远不被开发污染
2. 任何工作目录里，AI 一进来就知道**全部背景**

# 二、核心思路：分离「工具」与「工作」，用一张指路牌连接

```
工具（只读，一份）                  工作区（可写，任意多份）
GeeLo\                              D:\某项目\        E:\另一个项目\
├ AGENTS.md  ← 权威说明             ├ AGENTS.md      ├ AGENTS.md
├ 测试台\                           │   ↑ 指路牌      │   ↑ 指路牌
└ 送进编辑器\                       ├ 你的数据        ├ 你的资料
                                    └ 成果脚本        └ 成果脚本
```

**指路牌里只写两样东西：工具目录的绝对路径，和最要紧的一两条规矩。**
其余一律指回工具目录，不复制。

# 三、为什么是 `AGENTS.md` / `CLAUDE.md` / `GEMINI.md`

## 它们不是普通文档，是**约定俗成的 magic 文件名**

| 文件 | 谁会自动读 | 说明 |
|---|---|---|
| `AGENTS.md` | Codex / Cursor / Copilot / Cline / Zed / 通义灵码… | **跨厂商的通用约定**，覆盖面最广 |
| `CLAUDE.md` | Claude Code | 每次会话开始自动加载，还支持 `@路径` 导入 |
| `GEMINI.md` | Gemini CLI | 同上，但不认 `@` 导入 |
| `.github/copilot-instructions.md` | GitHub Copilot | 仓库级，位置固定 |

关键机制是**自动加载**。这正是问题 A 的解药——
你不用说"先了解项目"，因为它**已经**在上下文里了。

## ★ 谁当权威源：选覆盖面最广的那一个

**主体内容只写在 `AGENTS.md` 里**，其余三份都是指回它的短桩。

理由不是偏好，是算术：`AGENTS.md` 被最多工具认，把内容放在它那里，
"读到全文"的概率最高；而放在 `CLAUDE.md` 里，非 Claude 的工具就要多绕一跳。

★ 早期版本反过来做（`CLAUDE.md` 权威、`AGENTS.md` 当桩），
结果是**用 Codex / Cursor 的人拿到的是一句"请去读 CLAUDE.md"**——
它未必会去读，读了也可能只读一半。**桩要给少数派，不要给多数派。**

## 向上查找

Claude Code 会从当前目录**逐级向上**找 `CLAUDE.md`。所以：

- 在 `D:\某项目\脚本\` 开会话 → 也能读到 `D:\某项目\CLAUDE.md`
- 一个工作区放一份就够，子目录不用重复放

## 各文件的分工（别搞混）

| 位置 | 角色 | 内容 |
|---|---|---|
| 工具目录 `AGENTS.md` | **权威源** | 两个功能是什么、八条铁律、常用命令、目录地图 |
| 工具目录 `CLAUDE.md` / `GEMINI.md` / `.github/copilot-instructions.md` | **入口桩** | 一句"请先读 AGENTS.md" + 冗余的那两条铁律 |
| 工作区 `AGENTS.md` | **指路牌** | 工具的绝对路径 + 最要紧两条 + 本工作区约定 |
| 工作区 `CLAUDE.md` / `GEMINI.md` | **入口桩** | 一句"请先读同目录的 AGENTS.md" |

桩故意写得**极短**，不放内容。理由见下一节。

# 四、★ 最重要的一条原则：指路，不要复制

工作区的 `AGENTS.md` **绝不复制**工具那份的内容，只写：

```markdown
@D:\tools\GeeLo\AGENTS.md

（如果上面这行没有被自动加载，就直接打开读：`D:\tools\GeeLo\AGENTS.md`）
```

**为什么**：复制就会漂移。工具目录的规矩改了，十个工作区里还是老规矩，
而且没人知道哪份是对的。这个项目里早有先例——`配置读取.js` 的注释写着：

> 配置解析（主程序与自检**共用同一份**，避免两处规则漂移）

同一个道理，放大到文档层面。

**唯一允许重复的例外**：最要紧的一两条（这里是"必须实跑验证"和"跑通≠对"）。
因为万一 `@import` 没生效、或者 AI 偷懒没去读被指向的文件，
这两条也必须在场。**冗余是给失败路径兜底的，不是给正常路径用的。**

★ 注意那个 fallback 句子——`@import` 不是所有工具都支持，
所以后面跟一句"如果没被自动加载，就直接打开读 `<绝对路径>`"。
**任何依赖厂商特性的写法，都要配一句纯文本的退路。**

# 五、实现拆解：`new-workspace.js` 里每段代码为什么在

整个程序不到 150 行，没有依赖。逐段说：

## 5.1 工具目录路径从 `__dirname` 拿，不写死

```js
const TOOLBOX = __dirname;
```

程序自己在哪，工具目录就在哪。这样**工具目录整体改名或搬家后，
重跑一次本命令就能修好所有工作区**，不用改代码。

## 5.2 三道前置校验，每一道都对应一种真实误用

```js
if (!fs.existsSync(dir))              → 文件夹不存在
if (!fs.statSync(dir).isDirectory())  → 拖来的是文件不是文件夹
if (path.resolve(dir) === path.resolve(TOOLBOX)) → 目标就是工具目录自己
```

第三道最容易被忽略：人很自然会把工具目录自己拖上去试一下。
不拦住的话会覆盖掉权威版的 `AGENTS.md`——**那是灾难性的**，
因为所有工作区都指向它。

## 5.3 生成内容时把绝对路径**算出来**，不拼字符串

```js
const bench = path.join(TOOLBOX, '测试台', '跑GEE.js');
const brief = path.join(TOOLBOX, 'AGENTS.md');
```

然后插进模板。好处是路径分隔符、中文目录名都由 `path` 保证正确。

## 5.4 默认不覆盖，要覆盖得显式 `--force`

```js
if (fs.existsSync(p) && !force) { say('[跳过] ...已存在'); continue; }
```

工作区的 `AGENTS.md` 可能被人**手工加过本项目特有的约定**。
默认覆盖 = 悄悄毁掉别人的东西。**任何生成文件的工具都该默认不覆盖。**

## 5.5 写 UTF-8 **无 BOM**

```js
fs.writeFileSync(p, t.text, 'utf8');   // Node 的 'utf8' 不带 BOM
```

带 BOM 的 Markdown 有些解析器会把第一行标题吃掉；
更要命的是带 BOM 的 JSON 会让 `JSON.parse` 直接抛异常
（这个坑在 `送进编辑器\说明.md` 的坑 8 里有完整记录）。

## 5.6 结尾主动提醒局限

```
★ 注意：里面写的是**绝对路径**。工具目录以后挪了位置，
  在每个工作区重跑一次本命令即可（加 --force 覆盖）。
```

**已知局限要写在输出里，不要只写在文档里。** 人不会去翻文档。

# 六、怎么套用到你以后的别的工作流

一份可以照抄的清单：

## 6.1 先回答三个问题

1. **哪些是工具？**（稳定、只读、很少改）→ 进工具目录
2. **哪些是工作？**（每次都不一样、会产生垃圾）→ 进工作区
3. **AI 必须知道哪几条才能不犯错？** → 这就是"铁律"，最多八条，写进权威源 `AGENTS.md`

第 3 条最难。判断标准是：**这条规矩是不是"踩过才知道"的？**
如果 AI 靠常识就能想到，就不用写；只有反直觉的才值得占上下文。
本项目的八条铁律里，"跑通≠对"和".bat 必须纯 ASCII"都是踩出来的。

## 6.2 权威源 `AGENTS.md` 的骨架

```markdown
# <项目名>

**这个目录是工具，不是工作区。**

> 读到这份文件的 AI：不需要再问"要不要先了解一下项目"，看完这页就知道全部了。

## 有哪几个功能，谁在用
（一张表：功能 / 使用者是人还是 AI / 干什么）

## ★ 铁律
（最多八条。每条给一句"为什么"，最好附一个真实翻车案例）

## 常用命令
（可直接复制粘贴的完整命令行）

## 目录地图
## 深入文档指路（什么时候读哪份，别一上来全看）
## 环境事实（Node 版本、代理、shell 差异等本机特有的坑）
```

**长度控制在 150 行内。** 它每次会话都要占上下文，写成长篇反而降低遵守率。

## 6.3 注入器的骨架

```
node new-workspace.js <目标文件夹>
  ├ 校验：存在？是目录？不是工具目录自己？
  ├ 用 __dirname 算出工具目录与关键脚本的绝对路径
  ├ 生成 AGENTS.md（主体）：绝对路径 + 纯文本退路 + 最要紧的一两条 + 本工作区约定
  ├ 生成 CLAUDE.md / GEMINI.md（桩）：一句话指向同目录 AGENTS.md
  ├ 已存在则跳过（除非 --force）
  └ 输出里提醒"写的是绝对路径，工具目录搬家要重跑"
```

配一个 `.bat` 让人能**把文件夹拖上去**——比记命令行友好得多。
`.bat` 内容必须纯 ASCII（原因见 `测试台\说明.md` 坑 7）。

## 6.4 验收标准

做完之后，用这四条验：

- [ ] 在一个**全新的**工作目录开会话，不交代任何背景，直接提需求 → AI 能正确动手
- [ ] 工具目录在整个过程中**一个字节都没变**
- [ ] 工具目录改名/搬家后，重跑注入器能修好
- [ ] 把工具目录给别人，他的 AI 读完能自己配置

# 七、已知局限（诚实记下来）

| 局限 | 影响 | 缓解 |
|---|---|---|
| 写的是**绝对路径** | 工具目录搬家后所有工作区失效 | 重跑注入器（`--force`） |
| 多台电脑路径不同 | 工作区文件不能跨机器共用 | 每台机器各自跑一次注入器 |
| `@import` 非通用 | 有的工具不认 | 已配纯文本退路 |
| 依赖 AI 真的去读 | 读不读不由你控制 | 最要紧的两条**冗余写在指路牌里** |

---

# 八、一句话总结

**把"AI 需要知道的东西"当成一个可以部署的产物，而不是每次口头说的话。**

工具目录是权威源，工作区是部署点，注入器负责部署，`@import` 保证不漂移，
冗余的那一两条负责兜底。
